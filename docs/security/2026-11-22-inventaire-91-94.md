
Les branches `arena/*` existent encore à ce jour, mais **rien ne garantit qu'elles seront conservées**. Les SHA sont la référence durable ; les noms de branche ne le sont pas.

## 5. Ce qui rendait ces PR infusables

Trois raisons cumulatives, toutes mesurées :

1. **546 commits de retard** sur `main`, 2 à 7 conflits chacune.
2. **Aucune de leurs suites n'est branchée dans un workflow.** `test_p1_staging_harness.mjs` et `test_preview_deployment_selection.mjs` n'existaient que comme scripts npm. C'est le défaut de #119/#118, reproduit deux fois. #142 a corrigé le second.
3. **Tout le reste exige un environnement que la CI de ce dépôt n'a pas** : Preview réelle, secret de contournement Vercel, Clerk `sk_test_`, Neon Preview, PostgreSQL.

Le point 3 n'est pas un défaut des PR : c'est la nature d'une preuve d'intégration. Mais cela signifie qu'**elles ne peuvent pas être validées par la CI**, et une PR qu'on ne peut pas valider ne peut pas être fusionnée sur parole.

## 6. Ce qu'il faudrait pour rouvrir ce chantier

Deux chemins, selon ce que vous voulez :

**A. Récupérer les harnais sans les exécuter.** Les 4 workflows et 8 scripts peuvent être repris tels quels si vous acceptez de les livrer **non prouvés**, avec leurs entrées au registre des secrets. C'est faisable en une PR, mais c'est exactement le geste que j'ai refusé au lot E : livrer du code que personne n'a vu tourner. À vous de décider — c'est votre dépôt, pas le mien.

**B. Les rendre exécutables en CI.** Il faudrait : un environnement de Preview dédié, les secrets correspondants, et accepter que ces jobs aient besoin d'un relecteur manuel. Cela transforme la CI en quelque chose qui demande une approbation humaine — un choix d'organisation, pas de technique.

Les deux chemins partent des SHA du §4.

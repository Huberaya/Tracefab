## 1. Ce que fait cette PR

Elle arme `tracefab.active_organization_id` sur les routes de données. Motif, sur
une route représentative :

```diff
     const request = await withTracefabUserContext(user.id, user.email, (tx) =>
       scope === 'supplier'
         ? accessibleSupplierRequest(tx, user.id, requestId, DETAIL_SELECT, organizationId)
         : accessibleRequest(tx, user.id, requestId, DETAIL_SELECT),
-    );
+    organizationId);
```

Le quatrième argument de `withTracefabUserContext` pose
`set_config('tracefab.active_organization_id', ...)`. Sans lui, la RLS se rabat
sur **l'union des adhésions du compte** — le défaut de l'incident du
2026-10-17, qu'elle documente :

> un administrateur Clerk membre de Ginger et de Tracefab Recette Production
> voyait, depuis Ginger, le produit brouillon `RECETTE-DPP-20261017` qui
> n'appartient qu'au tenant de recette.

Avec une adhésion unique, les deux bornages sont indiscernables. C'est pourquoi
le défaut n'est apparu qu'en Production.

**Trois helpers sont durcis en fail-closed**, et c'est le bon sens de la
correction :

| Helper | Avant | Après |
|---|---|---|
| `accessibleRequest` | `{ in: organizationIds }` (union) | `if (!organizationId) return null` + un seul locataire |
| `accessibleSupplierRequest` | idem | idem |
| `currentSupplier` | repli sur la plus ancienne adhésion (`orderBy: created_at asc`) | `if (!organizationId) return null` |
| `document-scan-flow` | 3 transactions non armées | `ownerOrganizationId` passé aux trois |

C'est la preuve la plus sérieuse du dépôt : elle applique **la vraie chaîne des

```

ok  C. tenant A arme : le produit de B est INVISIBLE malgre une adhesion active a B
ok  C. tenant B arme : la matiere de B REDEVIENT visible (meme ligne, autre tenant)
```

**`scripts/test_active_tenant_context.mjs` — 16 contrôles verts.** Éprouvé **par
mutation** : en retirant le `if (!organizationId) return null` de
`accessibleRequest`, le test échoue (`actual: 1, expected: 0`). Il peut donc

## 3. La réserve — et elle me concerne

Le garde de non-régression admet **8 exemptions** à la règle « 4 arguments ».
Cinq sont légitimes : `me`, `organizations`, `invitations/accept`,
`supplier/organizations`, `supplier/onboarding` opèrent **avant** qu'un locataire
actif puisse exister.

Les trois autres sont des routes documentaires que **j'ai livrées dans le lot A
de #101**. La PR écrit :

```
// Exemptions temporaires (Phase 2) : ces 4 routes documentaires du lot A de
// #101 ... seront basculees des la fermeture complete de #101.
```

### Pourquoi ce n'est pas anodin

Ces routes s'appuient sur `tracefab_can_access_document`, qui appelle
`tracefab_can_access_org`, qui appelle `tracefab_is_org_member` :

```sql
SELECT EXISTS (
  SELECT 1 FROM organization_memberships m
  WHERE m.organization_id = p_organization_id
    AND m.user_id = tracefab_current_user_id()
    AND m.status = 'active'
);
```

**Ni `tracefab.active_organization_id`, ni un locataire armé.** C'est
exactement le bornage utilisateur que l'incident du 2026-10-17 dénonce.

### L'atténuation réelle

- `tracefab_can_access_document` exige `d.status = 'available'`. Un document
  **brouillon ou en cours de scan** n'est pas servi : dans le scénario de
  l'incident, le produit brouillon fuyait ; ici, seule une pièce déjà
  disponible peut l'être.
- `supplier/documents/*` borne par `currentSupplier`, désormais fail-closed.
- `documents/[documentId]/download.ts` : la route **vérifie** `can_access`
  avant de présigner, donc la fuite exigerait de connaître un UUID de document
  appartenant à un autre tenant **et** déjà disponible.

**Résiduel mais réel** : un compte membre de deux tenants qui connaît l'UUID
d'un document `available` de l'autre tenant le télécharge, sans en-tête de
locataire.

### Le correctif est trivial, et je ne l'applique pas seul

Les quatre routes ont déjà `requestedTenantId(req)` à portée : c'est le **même
en-tête** (`x-tracefab-organization-id`) que `requestedOrganizationId`. Il
suffirait de passer ce quatrième argument, et de remplacer l'exemption par
`requestedTenantId(req)`.

Je ne le fais pas dans cette analyse pour trois raisons :

1. Cela **change le comportement** de deux routes que j'ai livrées hier : un
   utilisateur sans en-tête de locataire perdra l'accès au lieu de le garder.
   C'est le but — mais c'est une décision, pas une correction mécanique.
2. Cela **échoue dans le sens sûr** : oublier l'en-tête donne 404, pas 200.
   Ce n'est pas une fuite silencieuse, c'est une gêne visible.
3. Votre décision au lot A était « livrer tel quel ». Je ne reviens pas dessus
   sans vous, et ici la question n'est pas la même : ce n'est plus « livrer ou
   non », c'est « resserrer maintenant ou après #101 ».

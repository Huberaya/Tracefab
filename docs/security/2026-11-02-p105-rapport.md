## 3. Cartographie des connexions runtime

Douze composants recensés (API serverless, cron, workers outbox, ingestion PLM/ERP, readiness,
rate-limit, migrations, élévation bornée, provisionnement des rôles, provisionnement de la clé,
suites de sécurité, outils de lecture) : `docs/security/2026-10-31-p105-connexions-runtime.md`.

Deux constats qui décident de la bascule :

- **un seul client Prisma** (`api/_lib/prisma.ts`) : il n'existe **aucun chemin de secours**
  applicatif. Soit `DATABASE_URL` porte `tracefab_app`, soit tout le runtime est privilégié ;
- les scripts d'exploitation **ne partagent pas** cette URL. `TF_ADMIN_URL` ne dit rien du
  rôle du runtime — c'est l'erreur qui avait brouillé P10.4.

La procédure de vérification en production (lecture stricte, `current_user`,
`session_user`, `pg_has_role`, appartenances, `_prisma_migrations`) est au §2 de ce document.

## 4. Plan de migrations à privilèges minimaux

- 68 migrations, appliquées dans l'ordre, **sans en réécrire une seule** ;
- exécutant : `tracefab_migrator` (`CREATEROLE`, `BYPASSRLS`, membre de `tracefab_worker`) ;
- **une seule** exception administrative, nommée et fermée (`MIGRATIONS_ASSISTEES`) :
  `20261028120100_worker_identity_not_forgeable`, avec élévation `SUPERUSER` bornée à sa
  transaction, révocation **relue**, puis rattrapage `GRANT tracefab_worker … WITH ADMIN
  OPTION, INHERIT TRUE, SET TRUE` sur la connexion d'administration ;
- refus explicite (sortie 3) si `TF_ADMIN_URL` ou `TF_ALLOW_ELEVATION=oui` manquent : rien
  n'est joué ;
- rattrapage d'une élévation laissée ouverte par un processus tué : le rôle est réabaissé,
  vérifié, puis la chaîne reprend ;
- `tracefab_app` ne peut **pas** migrer (mesuré : `42501 permission denied for schema public`),
  ni écrire dans `_prisma_migrations`.

## 5. Procédure de provisionnement

`docs/security/2026-10-31-p105-provisionnement.md` §2 (séquence rejouée) et §3 (les refus).

Ordre : base vierge → rôles (`provisionner_roles_db.mjs`, `TF_ALLOW_PROVISIONING=oui`) →
migrations sous le rôle de migration → clé d'identité (`provisionner_cle_identite.mjs`, clé
jamais affichée) → vérification en lecture seule.

`ensureAppRole` sépare désormais trois choses qui étaient confondues : **création** (CREATE),
**vérification** (lecture d'attributs, d'OID et d'objets possédés), **refus** (rôle divergent ou
appartenance existante). Le démarrage ne fait plus que vérifier.

## 6. Conception et preuves HMAC (R-A1)

`docs/security/2026-10-31-p105-hmac.md` ; migration `20261031120000_identite_hmac_liee_au_contexte`.

- le backend signe (HMAC-SHA256 sur contexte + identité + expiration), **la base vérifie** via
  `tracefab_identity_jeton_utilisateur(text)`, `SECURITY DEFINER`, `search_path` figé ;
- la clé vit dans `public.tracefab_identity_cles` : `tracefab_app` **n'a aucun privilège
  dessus** (lecture directe → `42501`), et un `REVOKE` explicite est reposé à chaque
  provisionnement, parce que `GRANT SELECT ON ALL TABLES` la rendrait lisible ;
- **aucune fonction de signature arbitraire** n'est exécutable par le runtime ;
- le jeton lie **identité + organisation + expiration** : rejouer un jeton dans un autre
  contexte est refusé, et un GUC forgé ne rend aucune identité en mode strict ;
- les 8 scénarios exigés (légitime, autre organisation, GUC forgé, jeton falsifié, expiré,
  rejeu dans un autre contexte, clé inaccessible, connexion physique réutilisée) sont couverts
  par 21 assertions (`test:p105:hmac`), plus 19 (`test:p105:jeton`) et 10
  (`test:p105:ingestion`).

**Réserve explicite maintenue** : le mode par défaut est **permissif**
(`tracefab_identity_politique.strict = false`). R-A1 n'est **pas** fermé en production tant que
`strict` n'a pas été basculé, ce qui exige d'avoir constaté `identityTokens.configured = true`
sur le déploiement réel. Le résidu est mesuré et affiché par la suite elle-même : en mode
permissif, un GUC forgé **sans** jeton est encore accepté.

## 9. Preuves négatives (aucune escalade)

- `tracefab_app` **ne peut pas** devenir SUPERUSER ni BYPASSRLS : `exigerConformite()` refuse un
  rôle préexistant qui porterait l'attribut, et l'assertion post-provisionnement le recontrôle ;
- `tracefab_app` **ne peut pas** s'accorder d'appartenance : toute appartenance est refusée
  avant écriture (B4), y compris transitive et quel que soit le `grantor` ;
- `tracefab_app` **ne peut pas** prendre le rôle propriétaire, `tracefab_migrator` ni
  `tracefab_worker` (contrôle par exécution, avec **témoin positif** : un `GRANT` temporaire
  rend `SET ROLE` possible, puis est révoqué — la mesure n'est donc pas vacante) ;
- sur `42710` (course sur `CREATE`), le code ne bascule **plus** sur un `ALTER ROLE` aveugle :
  il relit l'état et applique le même refus ;
- une cible **sans `LOGIN`** est refusée et reste sans `LOGIN` (test négatif ajouté).

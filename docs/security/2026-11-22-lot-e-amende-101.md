## 2. Comment les cinq fonctions ont été réinsérées

Elles avaient été retirées comme des blocs contigus, ce qui les rendait
récupérables, mais **trois d'entre elles avaient aussi perdu leur état ou leur
point d'appel** — c'est le piège que le document du lot E signalait sans le
chiffrer. Rétablir la fonction ne suffisait pas :

| Fonction | Ce qu'il fallait aussi rétablir |
|---|---|
| `dppIdentityPanel` | `state.dppIdentities`, `state.dppIdentitiesError`, et leur **chargement** dans `loadDpp` |
| `dppPublicationPanel` | son appel dans `renderDpp` |
| `createDppIdentity` | l'`addEventListener` sur `#dpp-identity-form` |
| `changeDppPublication` | les branches `suspend-dpp` et `withdraw-dpp` du routeur |
| `activateProduct` | sa branche `activate-product`, **et son bouton** dans la fiche produit |

Le chargement des identités mérite d'être noté : sa lecture est auxiliaire et
volontairement dégradable — un échec affiche l'erreur dans le panneau sans
masquer la préparation du dossier. Ce compromis est conservé tel quel.

## 3. Ce qui n'a pas été repris, et pourquoi

**Le garde anti-toast de `supplier-portal`.** #101 remplace

```js
function notify(message, isError = false) { state.toast = { message, isError }; if (state.toastTimer) clearTimeout(state.toastTimer); … }
```

par une version qui **supprime** le `clearTimeout`. Le commentaire de `main`
justifie ce garde par un échec intermittent mesuré de `test:p1:browser`.
Reprendre la version de #101 aurait rétabli précisément ce défaut. **Le garde de
`main` est conservé.**

## 4. Le catalogue : une union, pas un remplacement

C'est le point où le lot D et le lot E se rejoignent — et où la première
rédaction de ce chantier s'était trompée.

Le lot E appelle 38 clés qui **n'existent pas** dans le catalogue de `main`
(`dc*`, `dpPreview*`). Symétriquement, les cinq fonctions rétablies utilisent 32
clés que le catalogue de #101 avait **supprimées**. Aucun des deux catalogues ne
suffit :

| Catalogue utilisé | Clés brutes affichées |
|---|---|
| `main` seul (1180 clés) | **38** |
| #101 seul (1162 clés) | **30** |
| **union (1218 clés)** | **0** |

Les 38 clés ont été ajoutées aux sept langues, avec les traductions de #101.
Vérifié : `test:i18n` relève 1010 clés appelées, parité stricte à 2505 dans les
six locales complètes, **zéro introuvable**. Aucune clé de `main` n'a été
supprimée.

## 5. `test:mission-ui:states` : la raison d'être de cet amendement

Le script `scripts/test_mission_ui_real_states.mjs` existait sur `main` sans
porte d'entrée, et il ne pouvait pas être câblé : il attend
`retry-documents`, `open-upload-document` et `review-document`, qui n'existent
que dans le lot E. C'est ce que la CI avait démontré en échouant, à l'essai
précédent, quand la commande avait été ajoutée seule.

Les sélecteurs sont désormais présents. La commande est câblée :

```
"test:mission-ui:states": "node scripts/test_mission_ui_real_states.mjs"
```

**Réserve honnête : ce script n'a pas pu être exécuté dans cet environnement**
(aucun Chromium installé). Sa syntaxe est valide et tous les sélecteurs qu'il
attend sont présents dans les bundles, mais cela ne prouve pas qu'il passe. La
CI, qui installe un navigateur, le dira — et c'est elle qui a instruit le cas
précédent.

## 6. Le piège que ce document n'avait pas prévu

La première version de cette branche reprenait les deux bundles de #101 et y
réinsérait les cinq fonctions. **La CI l'a rejetée**, et le diagnostic vaut
d'être conservé : ces bundles ne sont pas seulement « ceux de #101 », ils sont
un **état antérieur de `main`**.

Le lot E a été écrit sur une branche ouverte avant plusieurs correctifs de
`main`. Les reprendre, même amputés des cinq suppressions, revient à revenir en
arrière sur tout ce que `main` a corrigé depuis. La CI a nommé trois d'entre
eux, un quatrième a été trouvé en instruisant le parcours DPP :

| Correctif de `main` perdu | Effet |
|---|---|
| `if (el.dataset.action) return;` sur `[data-product-id]` | le clic sur « Activer » rechargeait la fiche et écrasait la réponse du PATCH |
| repli `/assets/config/clerk.json` | une panne régionale de `/api/config` rendait la connexion impossible |
| fil `sourceDocumentId` (`documentOptions`, 2 champs, 2 payloads) | ni `traceability.documented` ni `evidence.product_data` ne pouvaient être satisfaits |
| `publishDppPublic` | le panneau de publication restauré était **inerte** : pas de POST |

Le troisième mérite d'être souligné : `test:brand-console:dpp-journey` est passé
de **32 à 38 vérifications** une fois le fil rétabli. Ce n'étaient pas des
vérifications qui échouaient, c'étaient des vérifications qui **ne s'exécutaient
plus** — le harnais s'arrêtait avant, faute de champ à remplir.

**Leçon transposable :** « régression » ne veut pas seulement dire « fonction
supprimée ». Un fichier repris d'une branche ancienne arrive avec **toutes** les
corrections qu'il n'a pas reçues entre-temps. Le bon test n'est pas « ce que le
diff supprime », mais « ce que le fichier ne contient plus par rapport à
`main` » — et seul un garde qui vérifie des invariants peut le dire.

## 8. Ce que cela ne règle pas

Le lot E amendé **ne ferme pas #101**. Les autres lots restent écartés : A, B, C
sont déjà sur `main` ; F et G n'apportent rien et G rouvrirait un déclencheur
`push` privilégié ; D n'a de sens qu'avec E, désormais satisfait ici.

Reste ouvert, et hors du périmètre de cette branche : la décision produit de
savoir si les cinq fonctionnalités doivent un jour disparaître. Si oui, ce sera
un commit dédié, motivé et revu — pas un effet de bord.

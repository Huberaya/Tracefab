## 1. R3 — trois scripts DPP hors classifieur → fermé

### 1.1 Ce qui était faux

Les trois scripts écrivent en base et sont lancés **directement** par
`package.json`, donc sans `scripts/run-db-suite.mjs` ni sa garde :

| Entrée `package.json` | Script | Écrit |
|---|---|---|
| `test:dpp:role-applicatif` | `test_dpp_role_applicatif.mjs` | `UPDATE dpp_records` |
| `test:dpp:branche` | `valider_branche_dpp.mjs` | tenant + produits |
| `db:mesure-dpp` | `mesure_effet_migrations_dpp.mjs` | parc + `UPDATE documents` |

Chacun portait une **liste noire** — un seul nom d'hôte, écrit en dur, et
surchargeable par la variable d'environnement `TF_HOTE_PRODUCTION` :

```js
const HOTE_PRODUCTION = process.env.TF_HOTE_PRODUCTION || 'ep-polished-night-…';
if (hote === HOTE_PRODUCTION || /^ep-polished-night/.test(hote)) { refus; }
```

Une liste noire est un refus **par défaut inversé** : tout ce qui n'a pas été
prévu est accepté. Mesuré : une autre base Neon, une base locale nommée
`tracefab_prod`, ou une chaîne portant `?hostaddr=` passaient toutes.

### 1.2 Correctif

Nouveau module `scripts/lib/garde_cible_ecriture.mjs`, branchement des trois
scripts sur `exigerCibleEcriture()`, qui applique :

1. **le classifieur commun** (`require-throwaway-db.mjs`, `classifyTarget`) :
   refus par défaut, refus inconditionnel de tout hôte managé (`*.neon.tech`,
   `*.supabase.*`, `*.rds.*`, …), refus des noms évoquant la production **y
   compris en local**, refus de `hostaddr`, refus d'un `host=` ambigu ;
2. **la concordance entre variables** : si `DATABASE_URL` et `TF_RLS_APP_URL`
   sont fournies, elles doivent désigner la **même base** — un script ne doit pas
   écrire là où il ne lit pas ;
3. **l'identité de cluster** : `TF_SYSID_ATTENDU` (facultatif) exige un
   `system_identifier` précis ; une identité **illisible** alors qu'elle est
   exigée est refusée (une vérité non établie n'est pas une autorisation) ;
4. **l'ordre** : la garde s'exécute **avant la première connexion** d'écriture ;
5. `TF_HOTE_PRODUCTION` **n'est plus lu** : une variable qui déplace la frontière
   de sécurité est une porte.

Codes conservés : `2` non exécuté (variable obligatoire absente), `3` cible
refusée. Aucune URL, aucun hôte, aucun identifiant n'est affiché — seulement la
classe, le nom de base et une empreinte tronquée.

### 1.3 Preuves demandées — toutes exécutées

| Contrôle négatif demandé | Assertion | Résultat |
|---|---|---|
| URL de production | `ep-polished-night-…neon.tech` → `managed_host` | refus |
| URL Neon | `ep-autre-branche-….neon.tech` → `managed_host` | refus |
| base locale non jetable | `127.0.0.1/tracefab_prod` → `production_name` | refus |
| | `?hostaddr=…` → `hostaddr_param` | refus |
| | `?host=a&host=b` → `ambiguous_host_param` | refus |
| variable contradictoire | deux bases jetables **différentes** → `contradictory_variables` | refus |
| | même base dans les deux variables | acceptée |
| identité de cluster inattendue | `TF_SYSID_ATTENDU=000…` → `unexpected_cluster` | refus |
| | identité illisible (port fermé) → `identity_unreadable` | refus |
| variable obligatoire absente | `missing`, levée de code 2 | refus |

**Aucune écriture lorsque la garde refuse — prouvé de bout en bout.** Une base
locale `tracefab_prod` est créée (nom que le classifieur refuse), on y pose une
table canari `canari_r3` avec **une** ligne, puis on lance les **trois** scripts
réels avec cette cible :

| Script | Code de sortie | Canari après |
|---|---|---|
| `test_dpp_role_applicatif.mjs` | **3** | 1 ligne |
| `valider_branche_dpp.mjs` | **3** | 1 ligne |
| `mesure_effet_migrations_dpp.mjs` | **3** | 1 ligne |

Les refus sont **instantanés** (moins de 5 s, y compris sur une cible Neon) :
preuve qu'aucune connexion réseau n'est tentée. La base canari est détruite en
fin de test.

## 2. R4 — `ensureAppRole()` → fermé

### 2.1 Ce qui était faux

`scripts/lib/tracefab_app_role.mjs` :

```js
const existe = await db.query('select 1 from pg_roles where rolname = $1');
if (!existe) CREATE ROLE tracefab_app … PASSWORD …
else         ALTER ROLE tracefab_app … PASSWORD …
```

Aucune lecture d'attributs, aucune preuve d'OID, aucune question sur ce que le
rôle possède : un `tracefab_app` **préexistant et étranger** voyait son **mot de
passe réécrit** et ses attributs rabattus.

### 2.2 Correctif

- état du rôle lu **une seule fois**, avant toute écriture : OID, attributs,
  objets possédés (`pg_shdepend`, `deptype = 'o'` — les GRANT sont de type `a`
  et ne comptent pas) ;
- rôle préexistant **privilégié** (`SUPERUSER`, `BYPASSRLS`, `CREATEROLE`,
  `CREATEDB`) ou **propriétaire d'objets** → `RolePreexistantRefuse`, **aucune
  écriture** : mot de passe et attributs intacts ;
- rôle préexistant ordinaire → réaffirmation (comportement historique) ;
- **OID relu après** : s'il a changé, l'appel échoue au lieu de valider ;
- vérification finale des attributs et de `LOGIN` ;
- surcharge de nom `{ role }` bornée à `tf_*` (même règle que
  `prepare_ci_db_role.mjs` / `TF_APP_ROLE_NAME`), et **droits applicatifs non
  accordés** dans ce mode : la surcharge ne sert qu'à éprouver le provisioning.

### 2.3 Preuves

| Cas | Attendu | Mesuré |
|---|---|---|
| rôle absent | créé, `LOGIN`, aucun privilège, mot de passe SCRAM | conforme |
| préexistant `SUPERUSER` | refus, **même OID**, **même empreinte de mot de passe**, attribut toujours présent | conforme |
| préexistant `BYPASSRLS` | idem | conforme |
| préexistant `CREATEROLE` | idem | conforme |
| préexistant `CREATEDB` | idem | conforme |
| préexistant **propriétaire** d'une table | refus, mot de passe et OID inchangés | conforme |
| préexistant ordinaire | réaffirmé, **même OID** (ni supprimé ni recréé) | conforme |
| OID qui change entre lecture et relecture | échec `change d'OID` (client simulé : branche non atteignable de façon déterministe sur un vrai serveur) | conforme |
| surcharge `postgres` | refus avant écriture ; rôle `postgres` inchangé (OID, attribut SUPERUSER, empreinte du mot de passe) | conforme |

Le test prend le **verrou de cluster** (il écrit dans `pg_authid`) et range tous
ses rôles `tf_r4_*` : « aucun rôle tf_r4_* résiduel ».

## 3. R5 — verrou fail-closed → fermé

### 3.1 Ce qui était faux

`run-db-suite.mjs` :

```js
catch (e) { console.error(`  AVERTISSEMENT — verrou de cluster non pris …`); }
```

Le verrou « demandé » était facultatif : exactement ce qu'il existe pour
empêcher restait possible. Et `pg_advisory_lock` **attendait sans limite** une
session concurrente — un blocage indéfini n'est pas non plus un comportement de
garde.

### 3.2 Correctif

- verrou demandé **avant le `spawn`** : aucun enfant ne démarre sans lui ;
- attente **bornée** (`TF_VERROU_ATTENTE_MS`, 30 s par défaut) via
  `pg_try_advisory_lock` en boucle — ajout d'une option `{ attenteMs }` à
  `verrouillerCluster`, sans changer le comportement par défaut des autres
  appelants ;
- toute erreur d'acquisition (connexion impossible, attente épuisée, module
  absent) → **`process.exit(3)`**, message « REFUS — verrou NON ACQUIS » ;
- `SIGINT`/`SIGTERM` : l'enfant est arrêté **puis** le verrou libéré (code 130 /
  143).

### 3.3 Preuves

| Cas | Attendu | Mesuré |
|---|---|---|
| A. verrou déjà détenu par une autre session | attente bornée puis exit 3, **suite non lancée** (témoin absent) | conforme (400 ms d'attente) |
| B. connexion impossible (port fermé) | exit 3, suite non lancée, **aucune URL affichée** | conforme |
| C. garde absente du disque (copie isolée du lanceur sans `lib/ephemeral-db.mjs`) | exit 3, pas de poursuite silencieuse | conforme |
| D. interruption SIGTERM | lanceur exit 143, **enfant arrêté**, verrou libéré, **aucun verrou orphelin** | conforme |
| E. succès | exit 0, verrou pris puis libéré | conforme |
| | échec de l'enfant (code 7) | code **7 propagé**, verrou libéré | conforme |
| | sans `--verrou-cluster` | aucun verrou pris, suite lancée | conforme |
| F. aucun chemin ne contourne | verrou avant `spawn`, `exit(3)` avant `spawn`, aucun « AVERTISSEMENT », `attenteMs` transmis, signaux traités, scripts shell verrouillés | conforme |

### 5.6 Recommandation

**Commit unique de l'arbre, R1/R2 documentés comme non exécutés.**

- Les trois risques visés sont fermés avec des preuves exécutées sur un cluster
  neuf, et chaque fermeture a son **contrôle négatif** ;
- aucune régression : les 20 suites exécutées passent, y compris celles des
  chantiers A et B ; les 6 dérives de compteurs échouent toujours ;
- le diff reste confiné à `scripts/` et `docs/security/` : rien dans `prisma/`,
  `api/`, `package.json`, `.github/` ;
- R7 (pas de branchement CI) est le vrai manque : à traiter dans le chantier
  suivant, car sans CI ces gardes ne sont vérifiées que par discipline.

Formulation honnête pour un message de commit : « ferme R3 (classifieur commun
sur 3 scripts DPP), R4 (preuve d'OID et refus des rôles préexistants
privilégiés), R5 (verrou fail-closed) ; section F et 3 suites Prisma non
exécutées (moteurs indisponibles) ; 6 suites non branchées en CI. »

**Aucun commit ne sera créé sans autorisation explicite.**

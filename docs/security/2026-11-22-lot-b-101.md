**`main` de référence :** `e1f510c`
**Résultat :** le déclencheur épinglé est **retiré du dépôt**, le garde est **renversé**, et il reste **une action qui vous appartient** — que je ne peux pas exécuter, et que je documente jusqu'au bout.

## 1. Ce que je pouvais faire, et ce que j'ai fait

Le dépôt contenait cette épingle, livrée en #143 :

```yaml
on:
  push:
    branches: ['arena/647ac97c-tracefab']
jobs:
  parcours:
    if: github.ref == 'refs/heads/arena/647ac97c-tracefab' && (... || vars.TF_PREVIEW_PUSH_ENABLED == '1')
```

Elle visait une branche de mission de la PR #101. Le raisonnement d'origine était honnête : `workflow_dispatch` exige que le fichier existe sur la branche par défaut, et #101 ne devait pas être fusionnée.

**Ce raisonnement n'a plus lieu d'être** : #101 est la dernière PR ouverte, et les lots A et C sont déjà dans `main`. Le fichier peut donc vivre sur `main`, où `workflow_dispatch` suffit.

### Ce qui a changé

| Avant | Après |
|---|---|
| `on: push: branches: [arena/647ac97c-tracefab]` + `workflow_dispatch` | **`workflow_dispatch` seul** |
| `if: ref == 'arena/647ac97c-tracefab' && (dispatch \|\| (push && vars.TF_PREVIEW_PUSH_ENABLED == '1'))` | **`if: event_name == 'workflow_dispatch'`** |

Le déclencheur `push` a été **supprimé, pas désactivé**. C'est la distinction qui compte : une voie fermée par une variable peut être rouverte par une variable. Une voie qui n'existe plus ne le peut pas.

La condition du job refuse maintenant tout événement autre que manuel, **explicitement**. Si quelqu'un ajoute un déclencheur au workflow sans toucher au job, le job ne s'exécutera pas.

## 2. Le garde a été renversé, pas contourné

`test:preview_journeys_guards.mjs` **exigeait** l'épingle :

```js
workflow.on.push.branches[0] === 'arena/647ac97c-tracefab'
```

Ce n'était pas une garde. C'était **la dette elle-même, verrouillée par un test** — un test qui aurait fait échouer la correction et rougi sur le retrait. Piège classique : le test décrit ce que le code fait, pas ce qu'il devrait faire.

Il vérifie désormais l'inverse :

```
ok  workflow declenche UNIQUEMENT manuellement — aucun push, aucun planning
ok  le job lui-meme refuse tout evenement autre que manuel
ok  aucune branche arena/* n est epinglee dans le declencheur ni dans le job
```

**Vérifié dans les deux sens**, comme le reste de ce dépôt :

- Épinglé réintroduit avec `arena/647cd97c-tracefab` (un SHA *différent*, pour ne pas seulement reconnaître le cas connu) :
  ```
  ECHEC workflow declenche UNIQUEMENT manuellement
  ECHEC aucune branche arena/* n est epinglee
  Gardes du harnais Preview : 2 ECHEC(S)
  ```
- Restauré :
  ```
  Gardes du harnais Preview : TOUTES LES PREUVES REUSSIES
  ```

Le garde refuse **n'importe quelle** branche `arena/*`, où qu'elle apparaisse dans le déclencheur ou dans le job. Il ne se contente pas de reconnaître celle qu'on vient de retirer.

## 3. Ce que je ne peux pas faire, et pourquoi

L'environnement GitHub `tracefab-clerk-test` autorise **quatre** branches :

```
64510415  arena/647ac97c-tracefab
64149524  arena/88857a44-tracefab
64151590  arena/f9effa2e-tracefab
63966314  main
```

Les trois branches `arena/*` **existent encore** sur le dépôt distant (vérifié par `git ls-remote`). Chacune d'elles, si l'on y pousse, peut déclencher un workflow qui demande l'environnement et y lit **six secrets de test**.

J'ai tenté de retirer ces politiques par l'API :

```
DELETE .../deployment-branch-policies/64510415
→ 403 Resource not accessible by integration
```

**Je n'ai pas les droits sur les paramètres d'environnement.** Ce n'est pas un contournement à trouver : c'est une action qui revient au propriétaire du dépôt.

## 4. Ce qui vous reste à faire — trois commandes

Après fusion de cette PR, ces trois commandes ne cassent plus rien : plus aucun workflow n'épingle ces branches.

```bash
# 1. Retirer les trois branches de la politique de deploiement
gh api -X DELETE repos/Huberaya/Tracefab/environments/tracefab-clerk-test/deployment-branch-policies/64510415
gh api -X DELETE repos/Huberaya/Tracefab/environments/tracefab-clerk-test/deployment-branch-policies/64149524
gh api -X DELETE repos/Huberaya/Tracefab/environments/tracefab-clerk-test/deployment-branch-policies/64151590

# 2. Verifier qu'il ne reste que main
gh api repos/Huberaya/Tracefab/environments/tracefab-clerk-test/deployment-branch-policies \
  --jq '.branch_policies[]|"\(.name)"'
# attendu : main

# 3. Optionnel : supprimer les branches elles-memes
git push origin --delete arena/647ac97c-tracefab arena/88857a44-tracefab arena/f9effa2e-tracefab
```

**L'ordre compte.** L'étape 3 après l'étape 1, jamais l'inverse : supprimer une branche encore autorisée par la politique d'environnement ne présente aucun danger, mais laisser une politique pointer sur une branche disparue rend le réglage illisible pour le prochain lecteur.

**Les relecteurs obligatoires (`Huberaya`) ne doivent pas être touchés** — vérifié comme en place, et c'est la barrière qui compte le plus : même une branche autorisée ne lit les secrets qu'après approbation.

Je ne l'ai pas touché pour trois raisons :

1. Ce n'est pas un workflow mais du code de garde d'accès : le verrou est là **pour empêcher** l'activation, et il tient.
2. Changer cette constante change le sel HKDF des capacités signées. C'est du code de sécurité **que personne n'a jamais vu fonctionner** — le modifier à l'aveugle serait pire que le laisser.
3. Vous avez tranché « livrer tel quel » au lot A. Je ne reviens pas sur une décision explicite sans vous.

`scripts/test_neon_preview_storage.mjs` pose la même valeur dans son environnement de test : cohérent, et sans effet hors test.

**Si les branches sont supprimées**, ce verrou devient inactivable — ce qui est sans conséquence tant que `PRIVATE_STORAGE_BACKEND` vaut `s3`. À traiter le jour où ce stockage servira, pas avant.

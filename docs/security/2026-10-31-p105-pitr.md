# P10.5 — Chantier F : PITR en lecture seule

Date : 2026-10-31 · Branche : `arena/96848462-tracefab`

Ce document **ne modifie aucune rétention**. Il décrit comment lire la fenêtre
réellement disponible, comment l'éprouver sans écrire, et ce qu'une restauration
doit valider pour compter comme preuve.

> 7 jours est une **proposition à vérifier**, pas une décision à appliquer.
> Aucune commande de ce document ne change `history_retention_seconds`.

---

## 1. Ce dont dépend la fenêtre

Neon conserve un journal de modifications par **branche**. La profondeur de ce
journal est un paramètre de la branche (`history_retention_seconds`), borné par
l'offre du projet. Conséquences opérationnelles :

- la fenêtre est **par branche**, pas par projet : une branche enfant hérite de
  ses propres réglages et peut avoir une fenêtre différente ;
- elle est **glissante** : la profondeur utile est « maintenant moins la
  rétention », pas la date de création de la branche ;
- elle ne se déduit **pas** du nom de l'offre : il faut la lire.

## 2. Lire la fenêtre (lecture seule)

### 2.1 Par l'API / la console

```bash
# lecture seule : aucun champ n'est modifié
neonctl branches get <branch-id> --project-id <project-id> --output json
```

Dans la réponse, lire `history_retention_seconds` (profondeur configurée) et la
fenêtre de restauration associée. La console affiche la même valeur dans
**Branch → Restore**.

À consigner dans le rapport d'exploitation : identifiant de branche, valeur
lue, horodatage de la lecture. Une fenêtre non datée n'est pas une mesure.

### 2.2 La borne réelle, mesurée par l'épreuve

Une valeur configurée n'est pas une valeur atteignable : si la branche a été
créée il y a trois heures, la fenêtre **utile** est de trois heures, quel que
soit le réglage. La seule mesure honnête est donc :

1. créer une branche de restauration à un instant T-1 h, T-6 h, T-24 h… jusqu'à
   l'échec ;
2. noter le plus ancien instant **restaurable avec succès** ;
3. supprimer immédiatement les branches de test (§ 4).

C'est cette valeur — « la plus ancienne restauration réussie » — qui doit
figurer dans le rapport, et non le paramètre de configuration.

## 3. Exercice de restauration, sans toucher à la production

Règle : **on ne restaure jamais sur la branche de production**. On crée une
branche fille à un instant passé, on la valide, on la jette.

```bash
# 1. créer une branche à un instant passé (aucun effet sur la production)
neonctl branches create \
  --project-id <project-id> \
  --parent <branch-id-production> \
  --timestamp "<AAAA-MM-JJTHH:MM:SSZ>" \
  --name "p105-restore-<horodatage>"

# 2. se connecter à la branche restaurée et valider (§ 3.1)
# 3. la supprimer
neonctl branches delete "p105-restore-<horodatage>" --project-id <project-id>
```

Notes :

- le nom de la branche de test porte l'horodatage : une ressource non nommée
  finit par rester ;
- une branche fille a **ses propres** rôles et mots de passe ; l'identité
  `tracefab_app` de production ne s'y rejoue pas telle quelle — c'est heureux,
  et c'est à prévoir dans la recette ;
- ne pas restaurer « pour voir ». Un exercice se planifie, se chronomètre et se
  documente.

### 3.1 Critères de validation d'une restauration

La restauration est **validée** si, sur la branche restaurée :

| # | Critère | Comment |
|---|---|---|
| 1 | les 68 migrations sont là, aucune en échec | sonde § 3a/3b |
| 2 | les 3 rôles `tracefab_*` existent avec leurs attributs attendus | sonde § 2 |
| 3 | `tracefab_app` n'a aucune appartenance | sonde § 4-5 |
| 4 | 53 tables sous RLS **forcée** | sonde § 7 |
| 5 | l'isolation inter-locataires tient | `test_rls_isolation.mjs` |
| 6 | l'ingestion refuse une identité forgée en mode strict | `test_p105_ingestion_isolation.mjs` |
| 7 | la clé HMAC est présente et illisible par le runtime | sonde § 8 |

Les critères 1 à 7 se mesurent avec les mêmes outils que sur base jetable : une
restauration qui ne passe pas les suites n'est pas une restauration, c'est une
copie.

### 3.2 Ce qu'une restauration ne valide **pas**

- elle ne valide pas la **perte** de données : restaurer récupère un état, il ne
  dit pas ce qui a été perdu entre cet état et maintenant ;
- elle ne valide pas les **objets hors base** (stockage privé, files, secrets
  Vercel) : ils ne sont pas dans le journal PostgreSQL ;
- elle ne valide pas la **durée d'indisponibilité** réelle d'une bascule de
  production — l'exercice se fait sur une branche fille, pas en basculant.

## 4. Hygiène des ressources

- toute branche de restauration créée pour l'exercice est **nommée**,
  **horodatée**, et **supprimée** dans la même session ;
- la suppression est vérifiée (liste des branches après coup), pas supposée ;
- aucune branche de test n'est laissée « au cas où » : une fenêtre de
  restauration pleine de branches de test rend la vraie restauration plus
  difficile à raisonner.

## 5. État de ce chantier

| Élément | État |
|---|---|
| lecture de `history_retention_seconds` | **non exécutée** — exige un accès Neon (interdit sans opérateur autorisé) |
| mesure de la borne réelle par épreuve | **non exécutée** — même raison |
| exercice de restauration | **non exécuté** |
| modification de la rétention | **aucune**, volontairement |
| proposition « 7 jours » | **non tranchée** : dépend de l'offre et du besoin réel de reprise |

Ce chantier est donc **documenté et outillé**, pas **prouvé**. Le critère de
sortie de la mission (« recette finale ») exige que ces trois lignes passent à
« exécutée », avec la valeur lue et la date de lecture, par un opérateur
autorisé.

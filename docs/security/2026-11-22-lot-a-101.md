## 1. La décision d'architecture, tranchée par le code

Le document de découpage annonçait un conflit : `withTracefabUserContext` (93
fichiers dans `main`) contre `withTracefabRequestContext` (23). Il fallait
« décider laquelle convient », présenté comme une décision d'architecture.

**Ce n'est pas un conflit.** Dans `api/_lib/context.ts` :

```ts
export async function withTracefabRequestContext(req, user, callback) {
  return withTracefabUserContext(user.id, user.email, callback, requestedTenantId(req));
}
```

`withTracefabRequestContext` **est** une enveloppe de `withTracefabUserContext`.
Les deux posent exactement les mêmes GUC (`tracefab.user_id`,
`tracefab.user_email`, `tracefab.active_organization_id`,
`tracefab.identity`). Il n'y a pas deux primitives : il y a une primitive et un
raccourci.

**Choix : `withTracefabUserContext` en forme explicite** dans `documents.ts`,
parce que le locataire actif est l'argument dont cette route dépend pour ne pas
fuiter, et que l'enveloppe le cache. `requestedTenantId(req)` y est lu une fois.

## 2. Ce qui a été livré (17 fichiers, 6 routes)

### 2.1 Deux corrections d'honnêteté qui n'étaient pas dans le découpage

Les plus importantes du lot, et elles n'étaient annoncées nulle part.

**a) La fausse attestation antivirus.** Dans `main`, `security-report.ts`
fabriquait un verdict :

```ts
const securityScan = meta.security_scan || {
  engine: 'Tracefab Forensics & ClamAV Engine v2',   // nom en dur
  engine, verifiedAt: ...
};
isEncryptedAtRest: true,                             // booléen en dur
```

`meta` vient de `documents.metadata`, **modifiable par le client** : elle n'a
jamais été une source de preuve. Et l'état `available` ne prouve ni quel moteur
a analysé le fichier, ni qu'il ait été analysé du tout.

Remplacé par `unavailableSecurityAttestations()` : `status: 'not_attested'`,
`clean: null`, `reason: 'server_attestation_not_recorded'`. **Un rapport qui ne
sait pas doit dire qu'il ne sait pas.** C'est un changement de réponse visible
pour les clients de l'API — c'est voulu.

**b) L'heuristique ne se déclare plus antivirus.** `analyzeDocumentBytes`
rendait `clean: true` / `status: 'clean'` sur un fichier sans signature connue.
Une heuristique qui n'a rien trouvé n'a rien prouvé. Elle rend désormais
`clean: false` / `status: 'error'` /
`engine: 'Tracefab heuristics (not an antivirus)'`, et le pipeline exige en plus
le verdict du scanner externe (`runAntivirusPipeline`).

Les trois détections restent intactes et testées : EICAR, exécutable déguisé en
PDF, PDF à script actif.

### 2.2 La correction d'isolation de `upload-intent`

`main` appelait `activeBrandOrganizationIds(tx, user.id)` puis retenait
`brandIds[0]`. Sur un compte membre de deux organisations, un dépôt demandé
depuis le locataire B était enregistré dans le locataire A, et le contexte
`tracefab.active_organization_id` n'était **jamais armé**. C'est l'union des
organisations du compte — exactement ce que `api/_lib/tenant.ts` documente comme
le défaut à ne pas reproduire.

Remplacé par `requireActiveTenant` + `tenantFilter`.

### 2.4 La distinction 401 / 500 dans `auth.ts`

`verifyToken` lève ses erreurs. Sans `catch`, un jeton forgé remontait en **500
`internal_server_error`** — indistinguable d'une panne. Le `catch` est étroit :
seules les raisons qui désignent le jeton deviennent 401. Une panne JWKS ou une
clé serveur invalide reste une 500, journalisable. Une raison **inconnue** est
traitée comme serveur, jamais comme un refus client.

## 3. Le groupe `preview-storage` — livré, non prouvé, et pourquoi

Décision : **livrer tel quel**, y compris le verrou de branche en dur.

```ts
export const PREVIEW_STORAGE_BRANCH = 'arena/647ac97c-tracefab';
// assertPreviewDatabaseTarget():
if (process.env.VERCEL_ENV !== 'preview'
    || process.env.VERCEL_GIT_COMMIT_REF !== PREVIEW_STORAGE_BRANCH
    || process.env.TF_PREVIEW_STORAGE_TEST_ONLY !== '1') throw ...
```

**Ce que cela signifie concrètement :** ce backend ne s'active que sur une
Preview de la branche `arena/647ac97c-tracefab`. Cette branche est une branche
d'une session antérieure. **Tant que `PRIVATE_STORAGE_BACKEND` vaut `s3` —
c'est-à-dire partout où personne ne le change — ce code est inerte.** Aucune
route de production ne l'atteint.

**Ce que je n'ai pas prouvé :** rien de ce trio n'a jamais tourné. Il exige
Clerk `sk_test_`, une base Preview approuvée par empreinte, et une table
`tracefab_preview_store` créée par `scripts/provision_preview_storage.ts` — trois
choses absentes de cet environnement. **Je ne sais pas si ces 277 lignes
fonctionnent.** Si le stockage PostgreSQL de Preview n'est jamais utilisé, elles
sont du poids mort ; si quelqu'un les active, il faudra les éprouver pour de bon.

## 4. Ce que la mesure a trouvé en chemin

Quatre fichiers du lot avaient **dérivé** dans `main` depuis la base de #101, et
`main` est allé **plus loin** que #101 sur deux d'entre eux :

- `storage.ts` : validation d'endpoint, refus des identifiants dans l'URL,
  `redirect: 'error'`, `AbortSignal.timeout(5000)`, classement
  `antivirus_timeout` / `antivirus_unavailable` / `antivirus_invalid_response`.
  **La version de #101 est plus ancienne.** Le patch a été appliqué **sur** la
  version de `main`, pas à la place.
- `auth.ts` : `withTracefabWorkerContext` déplacé vers `contexte-systeme.ts`,
  email vérifié par `verifiedPrimaryEmail`.

Un défaut d'intégration a été trouvé ainsi : `antivirus-scanner.ts` (version
#101) lit `scan.threat`, que `scanWithAntivirus` de `main` ne renvoyait pas.
`threat` a été ajouté à la version durcie, borné à 120 caractères.

## 5. Trois gardes ont protesté, et avaient raison

Aucun n'a été contourné ; chacun a été satisfait ou son contrat a été écrit.

1. **`test:route-context-coverage`** — 26/26 routes sans Clerk doivent être
   classées avec un contrat **vérifié**. `preview-storage/object` a reçu la
   classe `capability-preview-only`, dont le contrat exige les **trois** gardes
   (`usesPreviewPostgresStorage`, `assertPreviewStorageConfig`,
   `verifyPreviewCapability`) et le code `private_storage_unauthorized`. Retirer
   l'un des trois fait échouer le garde.
2. **`test:cross-tenant`** — modèle d'accès `CAPABILITY` avec justification
   écrite, et `verifyPreviewCapability` + `assertPreviewStorageConfig` exigés
   par le garde.
3. **`test:production-readiness`** — six variables lues par `api/` n'étaient pas
   documentées. Ajoutées à `docs/operations/variables-environnement.md`, avec
   pour chacune la conséquence de son absence.

Le quatrième, `test:storage:chantier10`, exigeait `clean === true` sur un fichier
sain — l'assertion même que la correction rend fausse. Réécrite pour vérifier
l'absence de **fausse alerte** et l'absence de **verdict fabriqué**, sans
toucher aux trois détections de menace.

## 7. Réserves — à lire avant de faire confiance

- **Aucune route n'a été exécutée contre une base.** Le harnais l'aurait exigé
  (PostgreSQL, Clerk, Playwright). Tout ce qui précède est de la lecture, du
  typage et de la mesure statique.
- **`api:typecheck` reste à 90 erreurs** faute de client Prisma généré. Je ne
  peux donc pas prouver que le lot compile — seulement qu'il **n'ajoute aucune**
  erreur à celles de `main`.
- **Le groupe `preview-storage` n'a jamais tourné.** Voir §3.
- **Le test de `[documentId]/validation.ts` n'existe pas.** Cette route écrit
  via `tracefab_add_dpp_claim` et `tracefab_link_dpp_claim_evidence` : je n'ai
  pas pu exécuter ces fonctions, et je ne prétends pas que le chemin d'écriture
  est correct.
- **`documents.ts` rend `validation: null` quand `take: 500` tronque.** Sur un
  très gros compte, la décision affichée reste la plus récente des 500 — jamais
  une plus ancienne présentée comme actuelle. C'est un compromis assumé, pas une
  preuve.

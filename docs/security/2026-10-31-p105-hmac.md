# P10.5 — Jetons d'identité signés (HMAC) — conception, preuves, limites

Date : 2026-10-31 · Branche : `arena/96848462-tracefab` · Base de preuve : PostgreSQL 17.10 jetable

Ce document répond à **R-A1**, le résidu laissé ouvert par P10.4. Il est le
référentiel de `api/_lib/identite-jeton.ts`, de
`prisma/migrations/20261031120000_identite_hmac_liee_au_contexte/` et de
`scripts/provisionner_cle_identite.mjs`.

---

## 1. Le problème, tel qu'il a été mesuré

`tracefab_current_user_id()` lisait `current_setting('tracefab.user_id', true)`.
Un GUC est une valeur que **l'appelant choisit**. P10.4 l'a mesuré sur base
jetable, avec le rôle applicatif réel (`tracefab_app`, sans SUPERUSER ni
BYPASSRLS) :

| Mesure | Contexte posé | Résultat P10.4 |
|---|---|---|
| M1 | identité légitime de A, organisation A | succès |
| M2 | identité de A, organisation B | refus `brand_product_role_required` |
| M3 | **identité forgée du propriétaire de B**, organisation B | **succès — 1 produit écrit** |
| M4 | aucune identité | refus `authentication_required` |

M3 est le point dur : la RLS fonctionne (elle cloisonne bien A et B), mais elle
croit l'identité qu'on lui donne. Le détenteur des identifiants du runtime
pouvait donc écrire chez n'importe quel locataire en appelant la fonction
d'ingestion `SECURITY DEFINER`.

## 2. La réponse : asymétrie signature / vérification

L'application **signe**, la base **vérifie**. La clé de signature n'est jamais
lisible par le rôle du runtime.

```
   api/_lib/context.ts ──signerIdentite()──► jeton ──► set_config('tracefab.identity', …, true)
                                                             │
                                          tracefab_current_user_id()
                                                             │
                                    tracefab_identity_jeton_utilisateur(text)  [SECURITY DEFINER]
                                                             │
                                            public.tracefab_identity_cles  [aucun GRANT à tracefab_app]
```

### Format

```
v1|<user_id>|<organization_id>|tracefab_identity|<exp>.<HMAC-SHA256 hexadécimal>
```

- `v1` : version du format. Toute autre valeur est refusée — c'est ce qui
  permettra de changer de schéma sans casser les anciens jetons en silence.
- `organization_id` : **lié au contexte**. La base compare ce champ à
  `current_setting('tracefab.active_organization_id')`. Un jeton émis pour A ne
  vaut pas pour B, même si l'utilisateur est le même.
- `exp` : secondes Unix, comparées à **l'horloge de la base**. Une horloge
  cliente en avance ne prolonge rien.
- Le séparateur corps/MAC est le **point**. Le champ d'usage porte donc un
  souligné : `tracefab.identity` contenait un point, coupait le corps en deux,
  et faisait refuser **tous** les jetons — y compris légitimes. Défaut mesuré,
  corrigé, et la raison est écrite dans la migration et dans le module.
- Durée par défaut : 60 s (`DUREE_JETON_SECONDES`). Une transaction dure des
  millisecondes ; une durée longue n'achèterait rien et élargirait la fenêtre
  de rejeu.

### Ce que la base refuse

- MAC absent, mal formé, ou calculé avec une autre clé ;
- corps modifié (le MAC porte sur le corps entier) ;
- jeton expiré ;
- jeton dont `organization_id` diffère du locataire actif ;
- jeton présenté alors qu'aucune clé **active** ne correspond.

### Ce que la base ne permet pas

- **Aucune fonction de signature arbitraire n'est accessible au runtime.** Le
  contrôle est un `proname LIKE 'tracefab\_%'` sur les fonctions exécutables par
  `tracefab_app` : `hmac`, `digest` et consorts appartiennent à l'extension
  `pgcrypto` et sont exclus du scan — sinon le contrôle produit un faux positif
  permanent (mesuré).
- **Aucun oracle.** `tracefab_identity_cles` n'accorde aucun privilège à
  `tracefab_app` : l'appel direct rend `42501 permission denied for table
  tracefab_identity_cles`. La fonction de vérification est `SECURITY DEFINER`
  avec `search_path = pg_catalog, public` figé, et n'expose ni la clé, ni un
  MAC, ni un motif exploitable.

### Le pooling

`set_config(..., true)` est **transactionnel**. Le jeton ne survit donc pas à la
fin de la transaction, et une connexion physique réutilisée par le pool ne
transporte pas l'identité de la requête précédente. C'est mesuré, pas supposé
(S8 ci-dessous).

## 3. Preuves exécutées

Toutes les preuves tournent sur une base **jetable** PostgreSQL 17.10, avec le
rôle applicatif réel `tracefab_app` (LOGIN, NOSUPERUSER, NOBYPASSRLS, 0
appartenance).

### 3.1 `scripts/test_p105_hmac_identite.mjs` — 15 assertions

| # | Scénario | Attendu | Mesuré |
|---|---|---|---|
| S1 | jeton légitime, identité + 2 produits | accepté | accepté |
| S2 | jeton de A présenté avec l'organisation B | refusé, 0 ligne de B | refusé |
| S3 | GUC `tracefab.user_id` forgé, **mode strict** | refusé | `authentication_required` |
| S4 | MAC faux / corps modifié | refusés | refusés |
| S5 | jeton expiré | refusé | refusé |
| S6 | rejeu du jeton dans un autre contexte | refusé | refusé |
| S7 | lecture de la clé par le runtime | `42501`, aucun oracle | `42501 permission denied for table tracefab_identity_cles` |
| S8 | connexion physique réutilisée (pooling) | aucun contexte résiduel | `tours=1`, même `pid` |
| N | **contrôle négatif** : jeter la même clé connue dans le contexte | jeton alors accepté | accepté |

Le contrôle négatif est ce qui distingue un test qui mesure d'un test qui
décore : si connaître la clé ne suffisait pas à produire un jeton valide, le
test ne prouverait rien sur le HMAC.

### 3.2 `scripts/test_p105_identite_jeton.ts` — 19 assertions

Le test précédent forge le HMAC **en Node**, dans le test. Il ne prouve pas que
le **code applicatif** signe comme la base attend. Celui-ci prend le chemin
réel : provisionnement par le script opérateur, signature par
`signerIdentite()`, vérification par PostgreSQL sous `tracefab_app`.

Points vérifiés : format `v1|…`, MAC hexadécimal de 64 caractères, échéance de
60 s, **échec fermé** sur clé trop courte et sur clé non hexadécimale, jeton
reconnu par la base, refus d'une clé différente, refus d'une autre organisation,
refus d'un jeton expiré, refus du GUC seul en mode strict, clé de test retirée.

La clé non hexadécimale méritait un test : `Buffer.from(x, 'hex')` **ignore
silencieusement** ce qui n'est pas hexadécimal. Une clé mal saisie de 64
caractères quelconques aurait produit un HMAC sur une clé **vide** — un jeton
vérifiable par quiconque connaît la clé vide. `cleIdentiteValide()` refuse,
`signerIdentite()` rend `null`, et l'application retombe en mode permissif où la
base applique sa politique.

### 3.3 `scripts/test_p105_ingestion_isolation.mjs` — 10 assertions

Le chemin fonctionnel réel (ingestion PLM/ERP sous `tracefab_app`) rejoué de
bout en bout, en mode permissif **et** en mode strict :

| Mesure | Mode | Résultat |
|---|---|---|
| M1 identité légitime de A sur A | permissif | succès, 1 produit |
| M2 identité de A sur B | permissif | `brand_product_role_required` |
| M3 GUC forgé du propriétaire de B | permissif | **accepté** — résidu assumé tant que `strict = false` |
| M3' GUC forgé sans jeton | strict | `authentication_required` |
| M3'' jeton valide du propriétaire de B | strict | succès (chemin normal) |
| M3''' jeton falsifié | strict | refusé, 0 écriture |
| — jeton expiré | strict | refusé |
| — jeton émis pour une autre organisation | strict | refusé |
| M4 aucune identité | — | `authentication_required` |

M3 est conservé **tel quel** dans le test : c'est la mesure du résidu, et elle
doit rester visible. Le passer en mode strict est une décision d'exploitation
(§ 4), pas un effet de bord d'un test.

## 4. Mode permissif → mode strict

`public.tracefab_identity_politique` porte un unique booléen `strict`
(`false` après migration). Il est **lisible** par le runtime — ce n'est pas une
donnée, c'est un réglage, et l'application doit pouvoir savoir dans quel mode
elle tourne — mais **non modifiable** par lui : la RLS ne crée aucune politique
`UPDATE`, l'ACL ne donne que `SELECT`, et une tentative d'écriture rend `42501`.
Mesuré par `scripts/test_rls_isolation.mjs` (4 assertions dédiées).

Ordre de déploiement — sans coupure :

1. appliquer la migration (crée les tables, la fonction, et laisse `strict = false`) ;
2. poser `TRACEFAB_IDENTITY_KEY` côté application ;
3. vérifier que l'application signe : `GET /api/internal/p2-readiness` doit
   renvoyer `identityTokens.configured = true` (booléen seul, jamais la clé) ;
4. vérifier en base que les jetons sont acceptés
   (`scripts/test_p105_identite_jeton.ts` sur une copie jetable) ;
5. alors seulement : `UPDATE tracefab_identity_politique SET strict = true` —
   par un rôle d'administration, jamais par le runtime.

Retour arrière : `strict = false` remet le comportement antérieur **pour les
appels sans jeton**. Un appel qui porte un jeton reste vérifié dans les deux
modes : le jeton n'est jamais un chemin qui *ajoute* de la permissivité.

**L'étape 5 n'a pas été exécutée en production et ne doit pas l'être avant que
l'étape 3 n'ait été constatée sur le déploiement réel.** Tant que `strict`
vaut `false`, M3 reste vrai : c'est écrit ici pour que personne ne lise « HMAC
livré » comme « R-A1 fermé ».

## 5. Limites — ce que le HMAC ne protège pas

- **Un vol de `TRACEFAB_IDENTITY_KEY`** permet de signer n'importe quelle
  identité pendant la durée de vie des jetons. Le HMAC déplace le secret (de la
  base vers l'application), il ne le supprime pas. Rotation : provisionner une
  nouvelle version (`provisionner_cle_identite.mjs`), puis retirer l'ancienne
  (`--retirer-anciennes`) une fois les deux périodes écoulées.
- **Pas de nonce** : un jeton peut être rejoué **dans son contexte** jusqu'à son
  échéance (60 s). Le rejeu dans un autre contexte, lui, est refusé.
- **Pas de révocation par utilisateur** : la révocation est par clé (version),
  pas par identité.
- **Le jeton ne dit pas ce que l'utilisateur a le droit de faire.** L'autorisation
  reste dans les politiques RLS et les gardes de rôle ; le jeton ne fait que
  rendre l'identité non forgeable.

## 6. Non vérifié en production

- que `TRACEFAB_IDENTITY_KEY` est réellement posée sur le déploiement Vercel ;
- que l'application en service émet des jetons (`identityTokens.configured`) ;
- la valeur de `tracefab_identity_politique.strict` sur la base réelle ;
- que la migration `20261031120000` est appliquée en production.

Ces quatre points se lisent avec
`docs/security/2026-10-31-p105-sonde-connexions-lecture-seule.sql` (sections 11
à 13) et `GET /api/internal/p2-readiness`, par un opérateur autorisé. Aucun
n'est vérifiable depuis ce dépôt.

## 4. Les quatre risques, un par un

### R6 — une interruption brutale laisse des ressources jetables

**Où.** `scripts/lib/ephemeral-db.mjs` (`creerBaseEphemere` → `nettoyageProuve`),
`scripts/lib/ephemeral-role.mjs` (`nomRoleEphemere`), `scripts/lib/base_jetable.mjs`
(`reinitialiserBaseJetable`). Le nettoyage est un `finally` : il ne s'exécute pas si
le processus est tué par un signal non interceptable.

**Scénario concret.** `kill -9` sur une suite en cours, ou coupure du runner CI.

**Gravité.** Faible : les objets laissés portent des préfixes réservés (`tf_*`,
`tf_garde_*`), ne contiennent que des données de test, et n'empêchent pas les
exécutions suivantes (noms aléatoires).

**Preuve exécutée** (`/tmp/pf/preuve_r6.mjs`, enfant tué par `SIGKILL`) :

```
AVANT  bases tf_* : [] | rôles tf_* : [] | verrous: 0
ENFANT a créé : { base: 'tf_r6_mvu9ylhk_be42e297db9f', oid: '126488',
                  role: 'tf_garde_r6_mvu9ylir_a43fffd3bfee' }
SIGKILL envoyé à 8884 — code de sortie = null signal = SIGKILL
APRES  bases tf_* : [ 'tf_r6_mvu9ylhk_be42e297db9f' ]
APRES  rôles tf_* : [ 'tf_garde_r6_mvu9ylir_a43fffd3bfee' ]
APRES  verrous consultatifs (session morte => libérés) : 0
RESIDU  base … : PRESENTE · rôle … : PRESENT · contenu : table preuve_r6, 1 ligne(s) de test
NETTOYAGE bases tf_* : [] | rôles tf_* : []      (nettoyage manuel prouvé)
Bases système/utilisateur intactes : [ 'postgres', 'tracefab_test' ]
```

Deux enseignements : le verrou consultatif **n'est pas** le résidu (PostgreSQL le
libère avec la session) ; le résidu est bien la base et le rôle.

**Correction proposée (non appliquée).** `scripts/nettoyer_ressources_jetables.mjs` :
énumère `pg_database` en `tf_*` et `pg_roles` en `tf_garde_*`, passe par la garde de
cible commune, refuse toute cible non jetable, **sort en dry-run par défaut**, exige
`--confirmer`, et ne supprime une base qu'après relecture de son OID. Jamais de
`DROP` sur `tracefab_test`, `tracefab_app` ou `tracefab_worker` (liste blanche
négative testée).

**Test démontrant.** `test_reprise_ressources_jetables.mjs` : (1) crée une base `tf_*`
et un rôle `tf_garde_*`, tue l'enfant, vérifie le résidu ; (2) lance le nettoyeur en
dry-run → résidu intact, sortie 0 ; (3) `--confirmer` → résidu supprimé, OID vérifié ;
(4) **contrôle négatif** : un rôle ordinaire préexistant et une base `tracefab_test`
sont intacts après passage.

### R9 — « reset sans `--verrou-cluster` » : l'invariant n'est tenu qu'à moitié

**Où.** `scripts/lib/base_jetable.mjs` : `reinitialiserBaseJetable()` prend le verrou
(l. 164) ; `detruireBaseProuvee()` ne le prend pas. `scripts/lib/ephemeral-db.mjs` :
`nettoyageProuve` (l. 224–240, appelé par `fermer()`) ne le prend pas non plus.

**Scénario concret.** Suite A détient le verrou de cluster et travaille sur une base
`tf_*`. Suite B (ou un test qui range ses fixtures) détruit une base sans verrou :
`DROP DATABASE … WITH (FORCE)` termine les sessions de A, qui travaille sur **sa**
base ? Non — sur *la sienne* uniquement… sauf que `detruireBaseProuvee` est aussi
appelée par des tests qui partagent des noms dérivés, et surtout : rien n'empêche
l'appel sur une base qu'un tiers utilise. La destruction n'est protégée que par la
preuve d'OID, pas par la sérialisation.

**Gravité.** Faible à moyenne : aucune atteinte à la production (garde de cible
commune en amont), mais perte silencieuse de travail d'une suite concurrente et
diagnostic trompeur (`57P01` au milieu d'une suite).

**Preuve exécutée n° 1 — le chemin « reset » respecte le verrou** (`/tmp/pf/preuve_r9.mjs`) :

```
verrou de cluster 738241901 : détenu par une session tierce
A. reinitialiserBaseJetable sous verrou tiers -> BLOQUE (il ATTEND le verrou : invariant respecté)
   après libération du verrou -> TERMINE (recreee, oid=126494)
```

**Preuve exécutée n° 2 — le chemin « destruction » l'ignore** (`/tmp/pf/preuve_r9b.mjs`) :

```
verrou de cluster détenu par une session tierce ; travail transactionnel en cours sur tf_r9_collateral_…
base.fermer() terminé en 119 ms malgré le verrou détenu
session de travail : {"ok":false,"code":"57P01","message":"terminating connection due to administrator command"}
base … présente après fermeture : non (lignes non validées detruites avec elle)
```

Contrôle croisé utile : deux mesures de `base.fermer()`, **toutes deux avec le verrou
détenu par un tiers**, donnent 149 ms puis 119 ms — aucune attente dans un cas où le
`reset`, lui, se bloque. La destruction ne « vérifie » donc rien.

**Correction proposée (non appliquée).** Dans `detruireBaseProuvee` et
`nettoyageProuve` : prendre `verrouillerCluster({ urlProprietaire, attenteMs })`
**avant** le `DROP`, relâcher dans un `finally`, et refuser (sortie 3) si le verrou
n'est pas acquis dans le délai — jamais « continuer quand même ». La preuve d'OID
reste, elle est complémentaire : le verrou sérialise, l'OID identifie.

**Test démontrant.** `test_destruction_verrouillee.mjs` : (1) avec le verrou détenu
par un tiers, la destruction **ne se termine pas** en 1 s ; (2) après libération, elle
se termine et la base a disparu ; (3) avec `attenteMs` court et verrou jamais libéré,
elle sort en 3 **sans avoir détruit** ; (4) le `reset` garde son comportement actuel
(contrôle de non-régression R9).

### R10 — reprise `XX000` de `prepare_ci_db_role` jamais exercée

**Où.** `scripts/prepare_ci_db_role.mjs`, fonction `executer(sql)` (l. 87–100) : 5
tentatives, temporisation `20·n + aléa`, uniquement sur `XX000`
(`tuple concurrently updated`).

**Scénario concret.** Deux exécutions simultanées de la préparation de rôle : l'une
des deux reçoit `XX000` sur `ALTER ROLE` et doit réessayer au lieu d'échouer.

**Gravité.** Faible — mais non mesurée jusqu'ici.

**Preuve exécutée** (`/tmp/pf/preuve_r10.mjs`), en deux temps :

```
1. ALTER ROLE concurrents (8) -> {"ok":4,"XX000":4}
   « tuple concurrently updated » dans le journal serveur : 4 occurrence(s)

2. prepare_ci_db_role.mjs x8 en parallele :
   #0..#7 exit=0  « Rôle tracefab_app préparé avant migrations : OID 16484, préexistant réaffirmé,
                     NOSUPERUSER, NOBYPASSRLS, NOCREATEROLE, NOCREATEDB. »
   « tuple concurrently updated » dans le journal serveur : 2 occurrence(s)
   nombre de sorties non nulles : 0

3. Etat final du role : {"rolname":"tracefab_app","rolbypassrls":false,"rolsuper":false,"rolcanlogin":true}
```

Lecture : `XX000` est **atteignable** (4/8 lors de la sonde directe) et il est
**apparu 2 fois pendant les exécutions réelles du script**, sans qu'aucune ne sorte en
erreur. La reprise fonctionne sous concurrence réelle. **Risque fermé sur le fond.**

**Résidu.** Aucune assertion automatisée ne rejoue ce scénario : le comportement est
prouvé une fois, pas protégé. `prepare_ci_db_role.mjs` étant déclaré intouchable, la
correction proposée est **un test seul** : `test_prepare_ci_role_concurrence.mjs`
(8 exécutions concurrentes, toutes doivent sortir en 0 ; le rôle final est unique,
sans `BYPASSRLS` ; contrôle négatif : un `TF_APP_PASSWORD` vide doit sortir en 2). Le
test ne peut pas *exiger* l'apparition de `XX000` (non déterministe) : il journalise
le nombre d'occurrences et se déclare « reprise observée / non observée » — jamais
« prouvé » quand elle n'est pas observée.

## 6. Plan de câblage CI (R7) — **présenté, non appliqué**

> Consigne respectée : **aucun workflow modifié**. Ce qui suit est une proposition
> soumise à autorisation.

**Contrainte de conception décisive.** Le job `verification` lance *tous* les scripts
`test:*` (sauf liste d'exclusion). Ajouter `test:gardes:*` rendrait ces suites
joignables **sans base**, donc rouges pour une raison d'environnement — exactement le
travers que `ci.yml` documente déjà pour `neon`/`staging`. Les 10 suites ont toutes
besoin d'une base (`DATABASE_URL` + `pg.Client`), et 4 d'entre elles exigent que la
base s'appelle littéralement `tracefab_test`
(`prepare_ci_db_role.mjs` refuse tout autre `pathname`).

**Proposition A (recommandée)** — un seul ajout dans `ci.yml`, job `base-de-donnees`,
**après** « Créer le rôle tracefab_app et deux locataires » :

```yaml
      - name: Gardes des ressources jetables et du verrou de cluster
        run: |
          set -e
          for s in test_garde_cible_ecriture test_verrou_fail_closed test_verrou_cluster \
                   test_concurrence_suites test_ressources_fixes_garde \
                   test_migration_atomicite_plm_dedup test_base_ephemere_garde \
                   test_role_ephemere_garde test_ensure_app_role_garde \
                   test_provisioning_role_app; do
            echo "== $s"
            node scripts/run-db-suite.mjs "scripts/$s.mjs"
          done
```

* **Effet attendu** : +10 suites, **+266 assertions**, exécution séquentielle mesurée
  **≈ 18 s** sur le cluster local (0,7 / 1,4 / 1,2 / 10,2 / 1,1 / 0,7 / 1,2 / 0,4 /
  0,4 / 1,0 s) ; aucun secret supplémentaire ; aucune connexion à la production ;
  aucun ajout d'entrée `package.json` (donc **aucun effet** sur la boucle du job
  `verification`).
* **Prérequis déjà satisfaits** en CI : base nommée `tracefab_test`, migrations
  appliquées, `tracefab_app` préparé, `TF_APP_PASSWORD` fourni.
* **Risque de faux rouge** : `test_concurrence_suites` lance deux suites en parallèle
  et prend le verrou — il doit rester **le seul** consommateur du verrou à cet instant
  (séquentialité du bloc `for` : oui). `test_ressources_fixes_garde` exige
  `prepare_ci_db_role` sortant en 2 sur rôle privilégié — comportement déjà couvert.
* **Coût** : +1 étape, +18 s, `timeout-minutes: 20` du job déjà en place (marge

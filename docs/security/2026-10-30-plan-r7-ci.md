## 2. Où elles sont branchées, et pourquoi là

Nouvelle étape dans le job **`base-de-donnees`** de `ci.yml`, **après**
« Créer le rôle tracefab_app et deux locataires » (`db:seed-rls`) et **après**
les épreuves RLS existantes : c'est le seul job qui dispose d'une base migrée,
d'un rôle applicatif réel et d'un mot de passe jetable.

```yaml
      - name: Gardes des ressources jetables, du verrou et de la reprise
        run: |
          set -e
          for suite in ...; do
            echo "== $suite"
            node scripts/run-db-suite.mjs "scripts/$suite"
          done
```

Trois raisons de ne **pas** créer d'entrées `package.json` `test:*` :

1. le job `verification` lance **tous** les scripts `test:*` qui ne sont pas
   explicitement exclus, **sans base** : une entrée `test:*` rendrait ces
   suites rouges pour une raison d'environnement — exactement le travers que
   `ci.yml` documente déjà pour `neon`/`staging` ;
2. la liste d'exclusion de `verification` est déjà longue et fragile ;
3. l'appel explicite rend la couverture lisible dans le workflow.

## 3. Correction obligatoire d'identité (R13)

Nouvelle étape, **avant** les suites RLS :

```yaml
      - name: Identité applicative — refus du superutilisateur
        run: node scripts/verifier_identite_app_ci.mjs
```

Le script vérifie, par connexion réelle :

* `TF_RLS_APP_URL` est **présente** (sinon sortie 2, blocage) ;
* `TF_RLS_APP_URL` ≠ `DATABASE_URL` (sinon sortie 3 : l'identité applicative
  serait l'identité d'administration) ;
* la session obtenue est `tracefab_app`, sans `SUPERUSER`, `BYPASSRLS`,
  `CREATEROLE`, `CREATEDB` ;
* les deux URL visent le **même** `system_identifier`.

Effet attendu : un job qui aurait perdu `TF_RLS_APP_URL` échoue **avant** les
assertions métier, au lieu de verdir sur une RLS contournée.

## 6. Ce que ce plan ne fait pas

* il ne touche ni `verification`, ni `socle`, ni `parcours`, ni aucun autre
  workflow (`audit-sql-privileges.yml`, `h1-4-postgres.yml`,
  `migrations-34-36-41.yml` inchangés) ;
* il ne crée aucun secret, ne lit aucun `secrets.*` ;
* il ne change pas `POSTGRES_USER` : le job a besoin d'un superutilisateur pour
  `CREATE ROLE`, mais **l'identité applicative** est désormais prouvée
  distincte et non privilégiée (étape du §3).
